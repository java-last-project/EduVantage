## 🛠 기술 스택 (Tech Stack)

* **Backend:** Java, Spring Boot, JPA, MyBatis
* **Frontend:** HTML5, CSS3, JavaScript, Thymeleaf, jQuery, Vue3, Pinia
* **Database:**  Oracle, PostgreSQL
* **Enviroment:**  AWS EC2, Ubuntu 26.04, Docker, Gradle, jenkins, minikube

<summary><b>&nbsp; 깃 브랜치 전략, 명령어 및 협업 규칙 펼쳐보기 (펼치기) </b></summary>

###  1. 브랜치 전략 (Branch Strategy)
- `main`: 배포 가능한 안정 버전만 관리하는 브랜치
- `dev`: 통합 개발 브랜치 (기본 작업 기준점)
- `feature/*`: 기능별 개발 브랜치 (개인 작업용)
  - `feature/course-*` (기승도)
  - `feature/exam-*` (기승도)
  - `feature/mypage-*` (송성민)
  - `feature/enrollment-*` (송성민)
  - `feature/instructor-*` (이지현)
  - `feature/admin-*` (이지현)
  - `feature/community-*` (박민서/기승도)
  - `feature/book-*` (유호빈)
  - `feature/auth-*` (유호빈)
  - `feature/notification-*` (안은혜)

---

###  2. Git 핵심 명령어
- `git switch [브랜치명]`: 지정한 브랜치로 이동
- `git branch`: 로컬 브랜치 리스트 및 현재 브랜치 확인
- `git branch [이름]`: 새 브랜치 생성
- `git push -u origin [이름]`: 원격 저장소에 브랜치 푸시 (최초 1회 설정 후 `git push` 사용 가능)

---

###  3. 협업 규칙 및 PR 워크플로우
> **주의사항:** 작업하는 브랜치는 절대 겹치면 안 됩니다! 만약 같은 기능을 여러 사람이 작업해야 한다면 `/feature/main-이름` 또는 `/feature/main-css` 등 구분되는 브랜치를 생성하세요. `dev`나 `main` 브랜치에서 직접 작업하는 것은 엄격히 금지됩니다.

#### **[작업 프로세스]**
1. **새로운 브랜치 생성**
    ```bash
    git switch dev
    git pull origin dev
    git switch -c feature/mypage
    git push -u origin feature/mypage
    ```
2. **초기 세팅 (Clone)**
    ```bash
    git clone '***.git'
    cd 프로젝트폴더
    ```
3. **작업 전 `dev` 브랜치 내용 반영 (Pull)**
    ```bash
    git fetch origin
    git merge origin/dev
    # 또는
    git pull origin dev
    ```
    *※ VIM 편집기가 뜬다면 `esc` → `:wq` 입력 후 엔터 (편집기를 안 뜨게 하려면 `git pull origin dev --no-edit` 사용)*  
    *※ 충돌(Merge Conflict) 발생 시 파일을 수정·저장한 후:*
    ```bash
    git add .
    git commit -m "이름) merge: dev 최신 변경사항 반영"
    git push
    ```
4. **브랜치에서 기능 개발 후 Commit / Push**
    ```bash
    git status
    git add .
    git commit -m "이름) feat: 마이페이지 회원정보 조회 구현"
    git push
    ```
5. **Pull Request (GitHub 웹에서 진행 권장)**
   - **base:** `dev` (합쳐질 대상)
   - **compare:** `feature/mypage` (내가 작업한 브랜치)
   - 리뷰어 지정 후 승인 시 **Squash and merge** 또는 **Create a merge commit**으로 병합 (초보 팀 기준 커밋을 하나로 묶어주는 Squash and merge 권장)

---

###  4. Git 커밋 메시지 규칙
1. **필수 태그 5가지 고정**
   - `feat`: 새로운 기능 추가 (예: `feat: 로그인 기능 및 세션 처리 구현`)
   - `fix`: 버그 수정 (예: `fix: 자동 채점 로직에서 발생하는 오류 수정`)
   - `style`: CSS 수정이나 코드 포맷팅 (로직 변경 없음)
   - `docs`: README나 문서 수정
   - `chore`: 초기 세팅, 라이브러리 추가 등 기타 잡일
2. **작성 기본 공식**
   - 제목은 `사용자ID) 태그: 작업내용` 형식으로 통일 (끝은 명사형으로 마감)
   - 예시) `kisd) feat: 교육센터 평가 자동 채점 모듈 추가`
3. **한 줄 요약 원칙**
   - 팀원들이 코드를 합칠 때 무슨 작업을 했는지 한눈에 파악할 수 있도록 간결하게 작성
   - 상세 설명이 필요한 경우 예외적으로 본문 추가 가능

#### **[커밋 메시지 예시]**
- **기능 추가 예시**
    ```text
    kisd) feat: 교육센터 평가 자동 채점 모듈 추가
    - 사용자가 제출한 답안과 DB의 정답을 비교하는 로직 구현
    - 채점 완료 후 마이페이지 점수 연동
    ```
- **버그 수정 예시**
    ```text
    hong) fix: 인프런 크롤링 데이터 중복 저장 오류 수정
    - 동일한 강의 데이터가 DB에 2번씩 INSERT 되는 문제 해결
    - 강의 고유 ID(PK) 중복 검사 로직 추가
    ```
